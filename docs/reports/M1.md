# Milestone 1 report: scaffold, audio engine, keyboard, MIDI, free play

## What works

- **Stack**: TypeScript (strict), React 19, Vite 8, Tailwind 4, Vitest, Playwright.
  Pages are code-split; the landing page loads none of the audio UI code.
- **Sample pipeline** (`scripts/build-samples.py`): builds Lite (2 velocity layers,
  3.7 MB) and Studio (4 layers, 18 MB) Ogg Opus tiers from the original
  Salamander V3 48 kHz/24-bit recordings, plus shared release and pedal samples
  (2.0 MB). The old Tone.js MP3s remain as a Compat tier for browsers without
  Opus. `npm run verify:samples` checks all 452 file entries by SHA-256.
- **Progressive loading**: the middle velocity layer of every zone loads first
  (nearest middle C outward), so the whole keyboard plays after 30 files, then
  the remaining layers stream in. Files are cached in IndexedDB; a second visit
  loads 258/258 Studio files from the device (tested).
- **AudioWorklet sampler** (`src/audio/worklet/dsp.ts`): 96 note voices + 48
  release/pedal voices, 4-point Hermite resampling, continuous velocity gain
  across layers (from measured layer levels), damper behaviour (keys from F6 up
  have no dampers), hammer-release and string-resonance release samples,
  pedal-down/up mechanism samples, sustain-pedal sympathetic resonance (24
  tuned comb resonators), sample-accurate scheduled notes, voice stealing.
- **Audio graph**: worklet → dry + generated room impulse → master → safety
  compressor → analyser → output. `latencyHint: 'interactive'`.
- **Input**: Web MIDI (note on/off, velocity, CC64 sustain, CC67 soft pedal,
  CC120/123 all-off, hot-plug, device choice), on-screen keyboard (pointer and
  multi-touch, glissando, velocity from strike position, roving keyboard focus),
  computer keyboard (v0.2 layout, Z/X octave, Space sustain). Every source goes
  through one input bus that posts to the worklet before touching React state.
- **Device setup page**: start audio, MIDI permission and device choice,
  keyboard size (from device name, by pressing lowest/highest key, or by hand),
  play-a-note test with velocity bars and pedal check, output device choice
  (`setSinkId`) and a Bluetooth/high-latency warning.
- **Free play**: piano with held-note readout and pedal state, output meter,
  sound controls (volume, room, touch dynamics, pedal resonance, release and
  pedal noise), metronome on the audio clock, record → replay → WAV export.
- **Platform handling already in place**: no-Web-MIDI banner (Safari/iOS),
  wireless-output banner, output-change banner, explicit Start audio step.

## Measured numbers

All measured in this cloud container: headless Chromium 141 on Linux, 4 vCPU,
no physical audio hardware, mock MIDI device.

| What | Result |
|---|---|
| Sampler render cost, 88 sustained voices + resonance (Node, `npm run perf:sampler`) | median 0.17 ms, p99 0.24 ms, max 1.0 ms per 128-frame block; budget 2.67 ms (6.3% at median) |
| Sampler load in Chromium, 10-finger chords with pedal held, 52 voices | mean 4.7%, max 9.1% of real time; 0 blocks over budget |
| Key-to-sound, mock MIDI → speaker (`getOutputTimestamp`) | median 33.9–37.5 ms across runs |
| of which: MIDI event → worklet post (main thread) | 0.0–0.1 ms |
| of which: audio path (next block + device buffers) | 33.9–37.2 ms |
| Device latency reported by this container's virtual audio output | base 10 ms + output 32 ms |
| Silence before the hammer attack, source → after trimming | 8–15 ms → 2.7 ms median to −40 dB |

### The 15 ms target

**Not verified, and not verifiable in this environment.** The container has no
sound card: Chromium's virtual output reports 42 ms of device latency, and
that sets the total. The app's own share is the input dispatch (≈0.1 ms) plus
at most one render quantum (2.9 ms at 44.1 kHz). On desktop Chrome with wired
audio, typical device figures are ~3 ms base latency and 5–10 ms output latency
(macOS CoreAudio, Windows WASAPI shared mode), which puts the expected total at
roughly 9–14 ms plus ~1 ms of USB MIDI transport. That is an estimate, not a
measurement. The Free play page measures the real number on every note
(Key-to-sound latency panel), so it can be confirmed on hardware in one minute:
connect a USB keyboard over a wired output, open Free play, play ten notes, and
read the MIDI median.

## Tests

- Vitest: 36 unit tests (sampler DSP behaviour, velocity curve, MIDI message
  parsing, keyboard-range detection, keyboard geometry, latency math).
- Playwright: 5 end-to-end tests with a mocked MIDI device (note, velocity,
  pedal, latency report; pointer play; computer keyboard; 10-finger stress;
  IndexedDB cache on reload).

## Known issues

- The 15 ms latency target is unmeasured on real hardware (see above).
- `Date.now()` is the only clock inside AudioWorkletGlobalScope, so the
  worklet's load figure has ±1 ms resolution per block. It averages out over a
  stats window; a single over-budget block between 2.0 and 2.7 ms can be
  counted as over budget (errs on the side of reporting a problem).
- Studio needs about 155 MB of memory for PCM. Phones default to Lite.
- Tails are capped (10 s in the bass, shorter higher up), so a note held
  longer than its cap fades early.
- Device labels for the Bluetooth check are empty until the browser grants
  media permission; until then the warning relies on reported output latency.
